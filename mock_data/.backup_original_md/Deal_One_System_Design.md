# Deal One: السيستم ديزين الكامل

**الإصدار:** 1.0 (النسخة الأولى)
**التاريخ:** 31 أكتوبر 2026
**النوع:** منصة إعلانات مبوبة للموبايل، بأقسام متعددة (عقارات، مواد بناء وكهرباء، خدمات، أجهزة منزلية وديكور، سيارات، ملابس وإكسسوارات)

---

## 1. نظرة عامة على المشروع

Deal One منصة إعلانات مبوبة شبيهة بـ Dubizzle، لكنها أكبر وأشمل، وتعمل على الموبايل بشكل أساسي. المنصة بتخدم نوعين من المستخدمين:

- **أفراد:** بيرفعوا إعلانات بيع أو إيجار أو شراء لأي حاجة (شقة، عربية، أجهزة، ملابس).
- **شركات ومنافذ:** شركات عقارية، مصانع وموزعين مواد بناء، مكاتب هندسية، منافذ بيع ملابس وأجهزة وقطع غيار، بيرفعوا وحداتهم ومنتجاتهم وخدماتهم.

### الأهداف
- إن الإعلان يوصل للمهتم بسرعة، ويتم التواصل بطريقة واضحة (شات داخلي أو خارجي).
- إن الشركات تقدر تختار طريقة البيع (دفع أونلاين أو تواصل).
- إن البحث يكون دقيق بالقسم والمنطقة والـ GPS.
- إن المنصة تكون آمنة من السبام والحسابات الوهمية، وتتحكم فيها الإدارة بالكامل.

### خارج نطاق النسخة الأولى
- الدفع أونلاين وإدارة الطلبات (مؤجل للمرحلة الثالثة).
- الاشتراكات المدفوعة للشركات.
- التقييمات والمراجعات.

## 2. المستخدمون والأدوار

| الدور | الصلاحيات |
|---|---|
| **مستخدم عادي (user)** | تصفح، بحث، شات، رفع إعلانات حسب حدوده اليومية |
| **حساب بيع (account owner)** | كل صلاحيات المستخدم + إدارة الإعلانات والفروع وطريقة البيع |
| **دعم (support)** | مراجعة وموافقة أو رفض الإعلانات، التحقق من الحسابات |
| **أدمن (admin)** | كل صلاحيات الدعم + تعديل الحدود والإعدادات + إدارة الأدوار |

### أنواع الحسابات (`account_type`)
- **فرد (individual):** إعلانات شخصية، حد يومي أقل.
- **شركة عقارية (company):** وحدات كتير، صفحة تعريفية، حد أعلى.
- **مصنع أو موزع (factory):** منتجات بكميات وأسعار، فروع متعددة.
- **مكتب هندسي أو مقدم خدمة (office):** خدمات ومناطق شغل.
- **منفذ بيع (store):** منتجات، عنوان فعلي، فروع، أو أونلاين.

الحساب الواحد ممكن يكون عنده **فروع متعددة** في أماكن مختلفة، كل فرع ليه عنوان وإحداثيات.

## 3. قرارات المنتج الأساسية (مثبتة)

| القرار | التفصيل |
|---|---|
| **طريقة البيع** | الحساب بيختار وقت إنشائه: **دفع أونلاين** أو **تواصل**. التغيير بيطبق فوراً على كل الإعلانات. |
| **قناة التواصل** | البائع بيختار لكل إعلان: **داخل التطبيق (شات)** أو **خارجي (واتساب/اتصال)**. |
| **الإعلانات** | **مجانية** في النسخة الأولى. |
| **الموافقة** | كل إعلان بيمر على **فريق الدعم** قبل النشر. |
| **التحقق** | **Cloudflare Turnstile** على كل الخطوات الحساسة. |
| **الحدود اليومية** | **الأدمن** بيحددها ويوافق عليها، وبتتطبق فوراً. |
| **التوقيت** | الحدود بتتصفر **منتصف الليل بتوقيت القاهرة** (`Africa/Cairo`). |
| **الشات** | **Real-time** عبر WebSocket. |
| **الفلترة** | بالمنطقة (يدوي) وبالـ GPS (المسافة). |

## 4. معمارية النظام

### 4.1 المكونات الرئيسية
1. **تطبيق الموبايل:** Android و iOS.
2. **Cloudflare:** DNS، حماية DDoS، WAF، Rate limiting أولي، Turnstile.
3. **الـ Backend API:** REST للعمليات العادية، WebSocket للشات.
4. **Redis:** الحدود اليومية، العدادات، Pub/Sub للشات، cache للبحث.
5. **PostgreSQL:** البيانات الأساسية، مع PostGIS للبحث الجغرافي.
6. **التخزين (S3 أو Cloudflare R2):** صور الإعلانات.
7. **FCM:** الإشعارات للموبايل.
8. **لوحة الإدارة:** ويب منفصل، بيتصل بنفس الـ API بصلاحيات الأدمن.

### 4.2 تدفق الطلب العادي
1. التطبيق بيبعت الطلب لـ Cloudflare.
2. Cloudflare بيتحقق من الـ WAF والـ rate limit، ولو مطلوب Turnstile بيتحقق منه.
3. الطلب يوصل للـ Backend، والـ middleware بيتحقق من الـ JWT والصلاحيات.
4. الـ Backend يتحقق من الحدود اليومية في Redis.
5. الـ Backend ينفذ العملية، ويكتب في PostgreSQL، ويزود العداد.
6. لو فيه إشعار، بيتبعت عبر FCM.

### 4.3 الاعتماد على الخدمات
- **الباك إند بيكون stateless** علشان يتعمل له scale أفقي.
- **الـ WebSocket** بيكون متصل بسيرفر معين، وRedis Pub/Sub بيوصل الرسالة للسيرفر الصح.
- **الصور** بتترفع مباشرة على التخزين عبر **presigned URL**، فالسيرفر ماينقلش الملفات الكبيرة.

## 5. الحسابات والمصادقة

### 5.1 التسجيل
- بالتليفون (OTP) أو الإيميل + كلمة مرور.
- **Turnstile** مطلوب قبل إرسال الـ OTP.
- بعد التسجيل، المستخدم بيكون عنده حساب شخصي، ولو عايز ينشر كشركة بيعمل **حساب بيع** جديد.

### 5.2 إنشاء حساب البيع
- المستخدم بيختار `account_type`.
- بيختار `sales_mode`: دفع أونلاين أو تواصل.
- بيدخل بيانات الحساب (الاسم، الوصف، الفروع).
- لو شركة أو مصنع، بيرفع الوثائق (سجل تجاري، بطاقة ضريبية، إلخ).
- الحساب بيكون في حالة `pending` لحد ما الدعم يوافق.

### 5.3 التحقق من الحساب (`verification_status`)
- **pending:** الحساب موجود، بس إعلاناته مش بتظهر للعامة.
- **approved:** الحساب متحقق منه، والإعلانات بتظهر.
- **rejected:** الحساب مرفوض، مع سبب.

### 5.4 الجلسات
- **Access token** قصير العمر (15 دقيقة).
- **Refresh token** طويل العمر (30 يوم)، بيتسجل في `USER_DEVICES`.
- عند تغيير كلمة المرور، كل الجلسات بتتلغي.

### 5.5 تغيير طريقة البيع
- الحساب بيتغير من `contact` لـ `online_payment` أو العكس.
- **الإعلانات مش بتتخزن فيها نسخة من طريقة البيع.** بتتقرا من الحساب وقت العرض.
- **تحذير:** لو اتحول لـ `online_payment`، الإعلانات اللي مفيهاش سعر ثابت بتتخفي من الدفع لحد ما تتعدل.
- **الطلبات والمحادثات القديمة** بتكمل بالطريقة اللي بدأت بيها.

## 6. الأقسام والإعلانات

### 6.1 الأقسام (Categories)
الأقسام شجرية (`parent_id`)، وكل قسم ليه حقول خاصة (`CATEGORY_FIELDS`).

| القسم | أمثلة على الحقول | أنواع الإعلان |
|---|---|---|
| **العقارات** | المساحة، عدد الغرف، الدور، الحالة | بيع، إيجار |
| **مواد البناء والكهرباء** | الماركة، المقاس، الكمية، الوحدة | منتج (بيع) |
| **الخدمات** | نوع الخدمة، المنطقة، سعر الزيارة | خدمة |
| **الأجهزة المنزلية والديكور** | الماركة، الحالة، الخامة | بيع، شراء |
| **السيارات** | الماركة، الموديل، السنة، الكيلومترات | بيع، شراء، قطع غيار، صيانة |
| **الملابس والإكسسوارات** | المقاس، اللون، الجنس، الحالة | بيع، منتج |

### 6.2 أنواع الحقول (`field_type`)
- `text`: نص حر.
- `number`: رقم (مع حد أدنى وأقصى اختياري).
- `select`: اختيار من قائمة (`options`).
- `bool`: نعم أو لا.

### 6.3 الإعلان (Listing)
الحقول الأساسية:
- العنوان، الوصف، السعر، العملة (جنيه).
- القسم، نوع الإعلان (`listing_kind`).
- المنطقة (`area_id`)، الفرع (`branch_id`) اختياري، الإحداثيات (`lat`, `lng`).
- قناة التواصل (`contact_channel`).
- الصور (من 1 لحد 10، حسب الإعدادات).

### 6.4 دورة حياة الإعلان

```
مسودة (draft)
   ↓ إرسال
قيد المراجعة (pending)
   ↓
فريق الدعم
   ├── موافقة → منشور (approved)
   │                 ├── مباع (sold)
   │                 ├── منتهي (expired)
   │                 └── مخفي (hidden)
   └── رفض → مرفوض (rejected) → يرجع لمسودة مع السبب
```

- **مدة الإعلان** بتتحدد من الإعدادات (مثلاً 30 يوم). بعدها بيتحول لـ expired، والبائع يقدر يجدده.
- **التعديل بعد النشر:** أي تعديل على السعر أو الصور بيرجع الإعلان لـ `pending` لمراجعة جديدة. التعديلات البسيطة (الوصف) تقدر تتطبق فوراً حسب الإعداد.
- **الإخفاء:** البائع يقدر يخفي إعلانه بنفسه، ومتقدرش ترجعه إلا لو اتوافق عليه.

### 6.5 قواعد الإعلانات الخاصة بطريقة البيع
| الحالة | القاعدة |
|---|---|
| حساب على `contact` | السعر اختياري، والتواصل بالشات أو الخارج |
| حساب على `online_payment` | السعر **إلزامي**، والكمية **إلزامية** للمنتجات |
| إعلان منتج بدون سعر بعد التحويل | يتخفي من الدفع، ويظهر بس بالتواصل لحد ما يتعدل |

## 7. التواصل والشات

### 7.1 قنوات التواصل
- **داخل التطبيق:** شات مسجل، والرسائل محفوظة في قاعدة البيانات.
- **خارج التطبيق:** رابط واتساب أو رقم اتصال، والبائع بيحدد الرقم.

### 7.2 الشات الفوري
- **WebSocket** للرسائل، وحالة الكتابة، وإشعارات القراءة.
- **Redis Pub/Sub** لتوزيع الرسائل بين السيرفرات.
- **FCM** للإشعارات لما التطبيق يكون مقفول.
- **محاولة إعادة الإرسال:** لو الاتصال اتقطع، الرسالة بتتبعت تاني لما يرجع.

### 7.3 حالات الرسالة
- `sent`: اتبعتت من التطبيق.
- `delivered_at`: وصلت للسيرفر والطرف التاني متصل.
- `read_at`: اتقرت.

### 7.4 قواعد المحادثة
- محادثة واحدة لكل (إعلان + مشتري).
- البائع بيشوف كل المحادثات الواردة على حساباته.
- **الحد اليومي للرسائل** (من الأدمن) بيتعد في Redis.
- **التبليغ:** المستخدم يقدر يبلغ عن محادثة أو إعلان (تقدر تضيفه في المرحلة الثانية).

## 8. البحث والفلترة

### 8.1 الفلاتر
- القسم والقسم الفرعي.
- نطاق السعر.
- نوع الإعلان (بيع، إيجار، ...).
- المنطقة (من القائمة).
- المسافة من موقع المستخدم (GPS).
- الحقول الخاصة بالقسم (مثلاً عدد الغرف للعقارات).
- الترتيب: الأحدث، الأقرب، السعر.

### 8.2 المنطقة والـ GPS
- **المنطقة:** اختيار يدوي من `AREAS`.
- **GPS:** لو المستخدم وافق على الموقع، بنستخدم الإحداثيات لترتيب النتايج حسب المسافة وفلتر نصف قطر (مثلاً 5 كم).
- **بدون GPS:** الفلترة بالمنطقة بس.
- الإعلان بياخد إحداثيات الفرع، أو موقع البائع لو مفيش فرع.

### 8.3 التنفيذ
- **PostGIS** للاستعلامات الجغرافية (`ST_DWithin`).
- **Index** على القسم والمنطقة والحالة (`status = approved`).
- **Cache** في Redis للنتايج الشائعة لمدة قصيرة (دقيقة أو اتنين).

## 9. الحدود اليومية

### 9.1 الأنواع
| النوع (`quota_type`) | الوصف |
|---|---|
| `listings` | عدد الإعلانات الجديدة في اليوم |
| `messages` | عدد الرسائل المبعوتة في اليوم |
| `contact_reveal` | عدد مرات إظهار رقم التواصل في اليوم |

### 9.2 الإدارة
- **الأدمن** بيحدد الحد لكل نوع حساب (`SETTINGS` بـ scope = account_type).
- التغيير **بيتطبق فوراً** على الطلبات الجاية.
- الحدود ممكن تكون **خاصة بحساب معين** (override) لو الأدمن عايز.

### 9.3 التنفيذ التقني
- **العدّاد في Redis:** المفتاح `quota:{account_id}:{type}:{YYYY-MM-DD}` بقيمة العداد.
- **التصفير:** الـ TTL بيتحسب لحد منتصف الليل **بتوقيت القاهرة** (`Africa/Cairo`).
- **الحد يتراجع:** لو العملية فشلت بعد ما العداد زاد، بنرجع العداد.
- **السجل الدائم:** `DAILY_QUOTAS` بيحفظ الاستخدام لكل يوم للتقارير.

### 9.4 ملاحظة مهمة
مصر بتدخل التوقيت الصيفي (UTC+3) في فصل الصيف، فالكود لازم يستخدم **الـ timezone الكامل** (`Africa/Cairo`) مش offset ثابت +2.

### 9.5 الرد عند الوصول للحد
الـ API بيرجع `429` مع رسالة واضحة، ومعاها وقت التصفير.

## 10. الأمان

### 10.1 Cloudflare Turnstile
- **الخطوات المحمية:** التسجيل، تسجيل الدخول، إرسال OTP، نشر الإعلان، إرسال أول رسالة لإعلان، إظهار رقم التواصل.
- **التحقق:** الـ token بيتبعت مع الطلب، والسيرفر بيتحقق منه عبر `siteverify` قبل أي عملية.
- **الـ token بيتستخدم مرة واحدة** وبيتحقق منه السيرفر في كل مرة.

### 10.2 حماية الـ API
- **Rate limiting:** على مستوى Cloudflare وعلى مستوى الـ API (لكل IP ولكل حساب).
- **JWT:** access token قصير، مع refresh token.
- **الصلاحيات:** middleware بيتحقق من الدور على كل endpoint.
- **Validation:** كل المدخلات بتتحقق منها على السيرفر، حتى لو الموبايل اتحقق منها.

### 10.3 حماية الصور
- **التحقق من النوع:** الصور بتتفحص من الـ magic bytes، مش بس الـ extension.
- **الحجم:** حد أقصى للصورة (مثلاً 5 ميجا).
- **التحويل:** الصورة بتتحول لـ WebP وبتتصغر لأحجام مختلفة.
- **الـ EXIF:** بيتشال منها بيانات الموقع الحساسة.

### 10.4 حماية البيانات
- **كلمات المرور:** مشفرة بـ bcrypt أو Argon2.
- **الوثائق:** الوثائق الرسمية للشركات (السجل التجاري وغيرها) بتتخزن في تخزين خاص، والوصول ليها للدعم والأدمن بس.
- **HTTPS** على كل الطلبات.
- **النسخ الاحتياطي:** يومي للـ DB، مع استعادة تجريبية كل شهر.

### 10.5 منع السبام والاحتيال
- **الإعلانات المكررة:** مقارنة العنوان والوصف والصور مع الإعلانات الموجودة.
- **الكلمات الممنوعة:** فلتر بسيط على العناوين والوصف.
- **البلاغات:** المستخدم يبلغ عن إعلان، والدعم يراجعه (المرحلة الثانية).

## 11. لوحة الإدارة

### 11.1 الشاشات
- **لوحة الرئيسية:** عدد الإعلانات قيد المراجعة، الحسابات الجديدة، إحصائيات اليوم.
- **الإعلانات قيد المراجعة:** قائمة مرتبة بالأقدم، مع عرض تفاصيل الإعلان والصور، وزر موافقة أو رفض مع سبب.
- **الحسابات:** قائمة الحسابات، التحقق من الوثائق، تعطيل الحساب.
- **الحدود اليومية:** جدول بكل نوع حساب والحد الحالي، مع تعديل.
- **الإعدادات:** مدة الإعلان، عدد الصور المسموح، أي قيم تانية.
- **السجل:** كل القرارات والتغييرات، مع المستخدم والوقت.
- **إدارة الأدوار:** إضافة وإزالة الدعم والأدمن (للأدمن بس).

### 11.2 صلاحيات الدعم مقابل الأدمن
| الإجراء | دعم | أدمن |
|---|---|---|
| موافقة ورفض الإعلانات | ✓ | ✓ |
| التحقق من الحسابات | ✓ | ✓ |
| تعطيل الحسابات | ✗ | ✓ |
| تعديل الحدود والإعدادات | ✗ | ✓ |
| إدارة الأدوار | ✗ | ✓ |

### 14.1 الجداول الرئيسية

### 14.2 العلاقات الأساسية
- `users` 1 ← N `accounts`
- `accounts` 1 ← N `branches`
- `accounts` 1 ← N `listings`
- `categories` 1 ← N `listings`
- `categories` 1 ← N `category_fields`
- `listings` 1 ← N `listing_values`
- `listings` 1 ← N `media`
- `listings` 1 ← N `conversations`
- `conversations` 1 ← N `messages`
- `accounts` 1 ← N `daily_quotas`

### 14.3 ملاحظات على التصميم
- **`listing_values`** بديل مرن للـ JSON، علشان الفلترة على الحقول الخاصة تبقى سهلة. ممكن تستخدم **JSONB** مع GIN index لو الحقول كتير.
- **الـ IDs** بتكون **UUID** علشان تبقى آمنة لو اتعرضت في الـ URLs.
- **الـ timestamps** بتتخزن بـ **UTC**، والعرض بيتحول لتوقيت القاهرة على الموبايل.
- **الـ soft delete** للإعلانات والحسابات، علشان السجل يفضل محفوظ.

### 14.4 الفهارس (Indexes)
- `listings(category_id, status, area_id)` للبحث الأساسي.
- `listings` GIST index على الإحداثيات للبحث الجغرافي.
- `messages(conversation_id, sent_at)` للشات.
- `daily_quotas(account_id, day, quota_type)` unique.
- `listing_values(field_id, value)` للفلترة على الحقول.

## 15. الأداء والتوسع

### 15.1 الأهداف
- زمن استجابة البحث: أقل من 500ms في المتوسط.
- زمن إرسال الرسالة: أقل من 200ms.
- دعم 10 آلاف مستخدم متزامن في البداية، مع إمكانية التوسع.

### 15.2 استراتيجيات
- **Cache:** نتايج البحث الشائعة في Redis، مع invalidation عند الموافقة على إعلان.
- **CDN:** الصور من Cloudflare، مع cache طويل.
- **Pagination:** كل القوائم بتتقسم، ومفيش تحميل كامل.
- **Queue:** العمليات الثقيلة (تحويل الصور، الإشعارات الجماعية) بتتعمل في background jobs.
- **Read replicas:** لو الـ DB بدأ يتحمل ضغط، القراءة بتتوجه لـ replica.

## 16. الـ Observability والمتابعة

- **Logs:** مركزية، مع تفاصيل كل طلب (بدون بيانات حساسة).
- **Metrics:** زمن الاستجابة، عدد الأخطاء، عدد الإعلانات الجديدة، معدل الموافقة.
- **Alerts:** لو الأخطاء زادت، أو الـ DB بطيء، أو الـ queue متراكمة.
- **Tracing:** لتتبع الطلب من الـ API للـ DB.
- **Dashboard للدعم:** عدد الإعلانات قيد المراجعة، ومتوسط وقت الموافقة.

---

## 17. الـ DevOps والنشر

- **Environments:** development، staging، production.
- **CI/CD:** كل commit على main بيتعمل له test وbuild، والـ deploy على staging تلقائياً، وعلى production بموافقة.
- **Infrastructure as Code:** Terraform أو ما يعادله.
- **Secrets:** في Vault أو Secret Manager، مش في الكود.
- **Backup:** يومي للـ DB، مع استعادة تجريبية شهرية.
- **Monitoring للـ Turnstile:** لو معدل الفشل زاد بشكل غير طبيعي، يتعمل alert.

## 20. قرارات معلقة تحتاج ردك

1. **حد الإعلانات الافتراضي** لكل نوع حساب (فرد، شركة، مصنع، مكتب، منفذ).
2. **حد الرسائل اليومي** والـ contact reveal الافتراضي.
3. **مدة الإعلان** بالأيام (30، 60، 90؟).
4. **عدد الصور** المسموح في الإعلان الواحد.
5. **الوثائق المطلوبة** للشركات والمصانع.
6. **حدود الإعلانات المكررة:** هل نرفض تلقائياً أو الدعم يراجع؟
7. **مزود الدفع** للمرحلة الثالثة.
8. **هل نحتاج تطبيق للشركات منفصل** ولا نفس التطبيق بتبديل حساب؟

## 21. الخلاصة

Deal One منصة إعلانات متعددة الأقسام، بتعتمد على موديل إعلان واحد مرن، وحقول خاصة لكل قسم. الميزات الأساسية في النسخة الأولى: حسابات بيع بطريقتين (دفع أونلاين أو تواصل)، شات فوري، بحث بالمنطقة والـ GPS، موافقة من الدعم، وحدود يومية تتحكم فيها الإدارة. التحقق بـ Turnstile على كل الخطوات الحساسة، والتوقيت كله على القاهرة.

النسخة الأولى تبني على أساس واضح يسمح بإضافة الدفع والاشتراكات بعدين من غير ما نغير الهيكل الأساسي.
