## 1. مقدمة

### 1.1 الغرض
تحدد هذه الوثيقة متطلبات البرمجيات التفصيلية والمواصفات الوظيفية وغير الوظيفية لمنصة **Deal One**. توفر الوثيقة مرجعاً هندسياً موحداً وملزماً لفرق تطوير واجهات الموبايل (Flutter)، والواجهات الخلفية (Modular Monolith Backend)، وفرق جودة البرمجيات (QA)، وفريق العمليات والرقابة.

### 1.2 نطاق المنتج (Product Scope)
Deal One هي منصة إلكترونية هجينة متعددة الأقسام تجمع المشترين والباحثين مع التجار والشركات والمصانع ومقدمي الخدمات عبر ستة أقسام رئيسية:
1. العقارات (Real Estate)
2. مواد البناء والكهرباء (Building Materials & Electricity)
3. الخدمات (Services)
4. الأجهزة المنزلية والديكور (Home Appliances & Decor)
5. السيارات (Cars / Automotive)
6. الملابس والإكسسوارات (Fashion & Accessories)

تعتمد المنصة معمارية: **النواة المشتركة (Shared Core) + القواعد المدفوعة بالقسم (Category-Driven Rules) + وحدات المعاملات المستقلة (Evolving Transaction Modules)**.

### 1.3 أهداف المنصة
1. توفير تجربة استكشاف وبحث متقدمة ترتكز على خصائص كل قسم مع دعم الترتيب والفلترة الجغرافية الدقيقة.
2. تمكين التجار والشركات من إدارة هويتهم التجارية، وفروعهم المتعددة، وفريق عملهم بكفاءة وموثوقية.
3. حماية السوق والمتعاملين عبر توثيق الحسابات التجارية، وفحص الإعلانات رقابياً قبل النشر، وحماية خصوصية المواقع.
4. بناء منصة مستقرة تطلق في المرحلة الأولى (V1) بنمط تواصل موثق (`contact_only`) وتتوسع مستقبلاً لإدراج التجارة والحجوزات.

### 1.4 خارج نطاق النسخة الأولى (Out of Scope for V1)
- بوابات الدفع الإلكتروني عبر الإنترنت (Online Payment Gateways).
- سلة التسوق والشراء المباشر (Cart & Checkout).
- إدارة الطلبات الكاملة (Order Management System).
- إدارة المخزون التفصيلي وتتبع حركات المستودعات (Inventory Tracking).
- محرك الحجوزات والمواعيد وجدولة الفترات الزمنية (Booking & Availability Engine).
- تسوية المستحقات ورد المدفوعات (Payouts & Refunds).
- تنبيهات البحث المحفوظ (Saved Search Alerts — مؤجلة للمرحلة الثانية V2).

### 1.5 التعريفات والمصطلحات المعتمدة
| المصطلح | التعريف |
|---|---|
| **النواة المشتركة (Shared Core)** | الأنظمة والخدمات الموحدة لكافة الأقسام (المصادقة، الحسابات، الوسائط، البحث، الشات، الرقابة، الحدود). |
| **قواعد القسم (Category Rules)** | المحددات والحقول والتحققات الخاصة بكل قسم على حدة. |
| **حساب البيع (Seller Account)** | الكيان التجاري أو الفردي الذي يملكه المستخدم لنشر الإعلانات وإدارة الفروع. |
| **الإعلان (Listing)** | العرض التسويقي العام الذي يكتشفه العميل عبر البحث والتغذية. |
| **المنتج في الكتالوج (Product)** | السلعة المعرفة في كتالوج التاجر (كيان تجارة V3 مفصول عن الإعلان). |
| **حالة الرقابة (`moderation_status`)** | حالة مراجعة الإعلان من فريق الدعم: `draft, pending, approved, rejected`. |
| **حالة النشر (`publication_status`)** | حالة إتاحة الإعلان للجمهور: `unpublished, published, hidden, archived`. |
| **حالة التوفر (`availability_status`)** | حالة الجاهزية للبيع أو الحجز: `available, reserved, sold, rented, out_of_stock, discontinued`. |
| **سجل الرقابة (`moderation_log`)** | السجل غير القابل للتعديل الذي يوثق قرارات الموافقة والرفض وأسبابها. |
| **الموقع الفعلي (Physical Location)** | الإحداثيات الحقيقية للسلعة أو الفرع (محمية ومحفوظة بسرية). |
| **الموقع الظاهر (Display Location)** | الموقع التقريبي المتاح للعامة لحماية الخصوصية. |
| **نطاق الخدمة (Service Area)** | النطاق الجغرافي الذي يغطيه مقدم الخدمة أو الموزع. |
| **Turnstile** | أداة التحقق الذكية من Cloudflare لمنع الروبوتات والسبام. |

## 2. الوصف العام للنظام

### 2.1 منظور النظام وهيكليته (System Perspective)
يتكون نظام Deal One من المكونات المتكاملة التالية:
1. **تطبيقات الموبايل (Flutter Apps):**
   - تطبيق العميل (Customer App): للتصفح، البحث، التفضيل، والتواصل.
   - تطبيق التاجر (Merchant App / Seller Context): لإدارة الحسابات، الفروع، الإعلانات، وفريق العمل، مع إمكانية التبديل بينهما بسلاسة للمستخدم الواحد عبر Monorepo مشترك.
2. **الواجهة الخلفية (Backend API):**
   - معمارية **المونوليث المعياري (Modular Monolith)** المبنية على حدود نطاقات أعمال واضحة (Bounded Contexts) تتواصل عبر واجهات برمجية داخلية محددة.
3. **قواعد البيانات والتخزين المؤقت:**
   - **PostgreSQL + PostGIS:** لتخزين البيانات العلائقية والاستعلامات الجغرافية.
   - **Redis:** لإدارة الجلسات، الحدود اليومية سريعة التصفير، والـ Pub/Sub للشات الفوري.
4. **خدمات الحماية والوسائط:**
   - **Cloudflare (DNS, WAF, Turnstile, R2):** لحماية المنصة وتخزين وسائط الإعلانات.
   - **Firebase Cloud Messaging (FCM):** لبث الإشعارات التشغيلية للأجهزة.
5. **لوحة الإدارة (Admin Dashboard):**
   - منصة ويب مخصصة ومؤمنة لموظفي الدعم والرقابة ومديري النظام.

### 2.2 أنواع المستخدمين والأدوار (User Roles & Access)
| فئة المستخدم | نطاق الصلاحيات |
|---|---|
| **الزائر (Guest)** | استكشاف الأقسام، تصفح الإعلانات، والبحث الجغرافي، دون صلاحية المراسلة أو إضافة إعلانات. |
| **المستخدم المسجل (Registered User)** | يمتلك هوية شخصية (`users`)؛ يحق له حفظ المفضلة، محادثة المعلنين، وإنشاء حسابات بيع. |
| **مالك حساب البيع (Account Owner)** | ينشئ ويدير حساب بيع تجاري (`accounts`)، يضيف الفروع، يدعو فريق العمل، ويرفع مستندات التوثيق. |
| **عضو حساب البيع (Account Member)** | مستخدم مسجل تم تعيينه في حساب بيع بصلاحيات محددة (`manager`, `lister`, `responder`). |
| **موظف الدعم والرقابة (Moderator / Staff)** | تدقيق وتوثيق الحسابات، اعتماد أو رفض الإعلانات، متابعة بلاغات المحتوى (`moderation_log`). |
| **مدير النظام (Admin)** | إدارة إعدادات المنصة، التحكم في الحصص والحدود اليومية، حظر الحسابات، وإدارة فريق الدعم. |

### 2.3 بيئة التشغيل والقيود العامة
- **نظام التشغيل للموبايل:** Android 9.0 (API level 28) فما فوق، iOS 15.0 فما فوق.
- **التوقيت الرسمي للنظام:** توقيت القاهرة القياسي (`Africa/Cairo`) مع المعالجة التلقائية للتوقيت الصيفي والشتوي.
- **العملة المعتمدة:** الجنيه المصري (EGP).
- **اللغة والاتجاه:** اللغة العربية كلغة رئيسية مع دعم كامل للاتجاه من اليمين لليسار (RTL).
- **الامتثال القانوني:** الالتزام الصارم بقانون حماية البيانات الشخصية المصري وقوانين التجارة الإلكترونية.

## 3. المتطلبات الوظيفية التفصيلية (Functional Requirements)

> نظام الترقيم: `FR-<النطاق>-<الرقم>`. الأولوية: **Must** (إلزامي للنسخة V1)، **Should** (مهم جداً)، **Could** (مخطط للمراحل اللاحقة V2/V3).

### 3.1 التسجيل والهوية والمصادقة (AUTH)

| المعرف | نص المتطلب | الأولوية |
|---|---|---|
| FR-AUTH-001 | يجب أن يدعم النظام تسجيل المستخدمين بالهاتف المحمول مع التحقق برمز OTP لمرة واحدة. | Must |
| FR-AUTH-002 | يجب أن يدعم النظام التسجيل بالبريد الإلكتروني وكلمة المرور المشفرة (Argon2 / bcrypt). | Must |
| FR-AUTH-003 | يجب إلزام فحص Cloudflare Turnstile على جميع عمليات إنشاء الحساب وتسجيل الدخول واستعادة كلمة المرور. | Must |
| FR-AUTH-004 | يجب أن تكون صلاحية رمز OTP محددة بـ 5 دقائق بحد أقصى 5 محاولات إدخال خاطئة. | Must |
| FR-AUTH-005 | يجب أن يصدر النظام `access_token` صالحاً لمدة 15 دقيقة، و`refresh_token` صالحاً لمدة 30 يوماً مخزناً بأمان. | Must |
| FR-AUTH-006 | يجب أن يتيح النظام استعراض جميع الجلسات والأجهزة النشطة للمستخدم مع إمكانية تسجيل الخروج من كل الأجهزة. | Should |
| FR-AUTH-007 | عند تغيير كلمة المرور، يجب إبطال جميع جلسات الـ refresh tokens النشطة ما عدا الجلسة الحالية. | Must |

### 3.3 حسابات البيع وتعدد الكيانات وتوثيقها (ACC & VERIFICATION) (ADR-004, ADR-005)

| المعرف | نص المتطلب | الأولوية |
|---|---|---|
| FR-ACC-001 | يجب أن يتمكن المستخدم المسجل من إنشاء حساب بيع تجاري واحد أو أكثر بشكل مستقل تماماً. | Must |
| FR-ACC-002 | يجب تصنيف حساب البيع إلى أحد الأنواع المعتمدة: `individual`, `company`, `factory`, `office`, `store`. | Must |
| FR-ACC-003 | يجب حصر نمط المعاملات لكافة الحسابات في النسخة الأولى (V1) في نمط التواصل فقط (`contact_only`). | Must |
| FR-ACC-004 | يجب أن يدعم حساب البيع إضافة فرع أو فروع متعددة تشمل الاسم، العنوان، المنطقة (`area_id`)، والإحداثيات. | Must |
| FR-ACC-005 | يجب أن يدعم حساب البيع إضافة فريق عمل (`account_members`) بأدوار محددة (`manager`, `lister`, `responder`). | Must |
| FR-ACC-006 | يجب إلزام حساب البيع برفع مستندات التوثيق الرسمية وفقاً لنوعه (سجل تجاري، بطاقة ضريبية، رخصة مزاولة). | Must |
| FR-ACC-007 | يجب أن يمر حساب البيع بحالات التوثيق الثلاث: `pending`, `approved`, `rejected` في جدول `accounts`. | Must |
| FR-ACC-008 | يُمنع منعاً باتاً ظهور إعلانات الحسابات التجارية للعامة في التغذية والبحث ما لم تكن بحالة `approved`. | Must |
| FR-ACC-009 | توثيق حساب البيع يثبت الصفة القانونية للكيان التجاري، ولا يعتبر إثباتاً تلقائياً لملكية أو أصالة كل سلعة معلنة. | Must |
| FR-ACC-010 | يجب عزل الحصص اليومية والحدود وسجلات التدقيق لكل حساب بيع يمتلكه المستخدم باستقلالية تامة. | Must |
| FR-ACC-011 | يحق لمدير النظام تعطيل الحساب التجاري إدارياً (`is_active = false`)، مما يؤدي فورياً لإخفاء كامل إعلاناته. | Must |

### 3.5 الإعلانات وإدارة دورة الحياة (LST) (ADR-003, ADR-006, ADR-007, ADR-008)

| المعرف | نص المتطلب | الأولوية |
|---|---|---|
| FR-LST-001 | يجب أن ينشئ المعلن الإعلان تحت حساب بيع محدد مع اختيار القسم والقسم الفرعي. | Must |
| FR-LST-002 | يجب إدخال البيانات الموحدة: العنوان، الوصف، السعر، العملة (EGP)، والنوع (`sale, rent, buy, service, product`). | Must |
| FR-LST-003 | يجب فصل الموقع الفعلي الدقيق (`physical_lat`, `physical_lng`) عن الموقع الظاهر للجمهور (`display_lat`, `display_lng`). | Must |
| FR-LST-004 | يجب حماية خصوصية العقارات السكنية والأفراد بعدم نشر إحداثياتهم الدقيقة وعرض الموقع التقريبي فقط (`area_id`). | Must |
| FR-LST-005 | يجب تحديد قناة التواصل للإعلان: داخل التطبيق (شات فوري) أو خارجي (واتساب / هاتف محمول). | Must |
| FR-LST-006 | يجب أن يخضع كل إعلان لثلاث حالات مستقلة: `moderation_status`, `publication_status`, `availability_status`. | Must |
| FR-LST-007 | تتحدد قيم `moderation_status` كالتالي: `draft, pending, approved, rejected`. | Must |
| FR-LST-008 | تتحدد قيم `publication_status` كالتالي: `unpublished, published, hidden, archived`. | Must |
| FR-LST-009 | تتحدد قيم `availability_status` كالتالي: `available, reserved, sold, rented, out_of_stock, discontinued`. | Must |
| FR-LST-010 | يجب دعم رفع من 1 إلى 10 صور للإعلان الواحد عبر روابط رفع سحابية مباشرة وموقعة (Presigned URLs). | Must |
| FR-LST-011 | عند تعديل بيانات جوهرية لإعلان معتمد (سعر، صور، قسم)، يتحول تلقائياً إلى `moderation_status = pending`. | Must |
| FR-LST-012 | لا يظهر الإعلان في البحث والتغذية العامة إلا إذا تحققت كافة شروط الاعتماد والنشر والتوفر وصلاحية الحساب. | Must |

### 3.6 الرقابة وتدقيق المحتوى وسجل القرارات (MOD) (ADR-007)

| المعرف | نص المتطلب | الأولوية |
|---|---|---|
| FR-MOD-001 | يجب أن يعرض طابور المراجعة لموظفي الدعم جميع الإعلانات بحالة `moderation_status = pending` مرتبة بالأقدمية. | Must |
| FR-MOD-002 | عند اعتماد الإعلان، يقوم الموظف بتغيير حالته إلى `approved` مع تسجيل القرار في `moderation_log`. | Must |
| FR-MOD-003 | عند رفض الإعلان، يجب إلزام الموظف باختيار سبب رفض قياسي وملاحظة توضيحية تسجل في `moderation_log`. | Must |
| FR-MOD-004 | يجب أن تظل كافة سجلات الرفض والاعتماد السابقة للإعلان محفوظة في `moderation_log` ولا تحذف عند التعديل. | Must |
| FR-MOD-005 | عند رفض الإعلان، يُرسل إشعار فوري للمعلن يوضح سبب الرفض مع تمكينه من تعديل الإعلان وإعادة إرساله. | Must |
| FR-MOD-006 | يجب أن يوثق جدول `moderation_log`: معرف السجل، معرف الهدف، هوية الموظف، الإجراء، سبب الرفض، والختم الزمني. | Must |

### 3.7 البحث والاستكشاف الجغرافي (SRC & GEO) (ADR-006)

| المعرف | نص المتطلب | الأولوية |
|---|---|---|
| FR-SRC-001 | يجب أن يدعم النظام البحث بالكلمات المفتاحية في العنوان والوصف مع معالجة اللغة العربية ومرونتها. | Must |
| FR-SRC-002 | يجب دعم فلترة النتائج بالأقسام، نطاق الأسعار، المناطق الإدارية (`area_id`)، وتاريخ الإعلان. | Must |

| FR-SRC-006 | يجب حصر نتائج البحث العامة حصرياً في الإعلانات المطابقة لشروط النشر والاعتماد وحسابات التجار الموثقة. | Must |
| FR-SRC-007 | ميزة حفظ معايير البحث وتنبيهات الإعلانات الجديدة (Saved Searches) تدرج ضمن المرحلة الثانية (V2). | Could (V2) |

### 3.8 المحادثات الفورية والتواصل (CHT) (ADR-008)

| المعرف | نص المتطلب | الأولوية |

## 4. المتطلبات غير الوظيفية (Non-Functional Requirements)

### 4.1 الأداء وسرعة الاستجابة (Performance)
- زمن استجابة الـ API لعمليات القراءة والبحث: أقل من 300 مللي ثانية (95th percentile).
- زمن تسليم الرسائل عبر الـ WebSocket: أقل من 150 مللي ثانية في ظروف الشبكة الطبيعية.
- دعم ما لا يقل عن 10,000 مستخدم متصل في الوقت نفسه (Concurrent Users) مع إمكانية التوسع الأفقي لخدمات الـ API عديمة الحالة (Stateless).

### 4.2 الأمان وحماية البيانات (Security)
- تشفير كافة الاتصالات خارجياً وداخلياً باستخدام TLS 1.3.
- كلمات المرور تشفر بخوارزمية متينة (Argon2id أو bcrypt بمعامل تكلفة ملائم).
- حماية كافة المنافذ الحساسة بـ Cloudflare Turnstile ومعدلات طلب محكمة (Rate Limiting).
- منع هجمات حقن التعليمات (SQL Injection) باستخدام استعلامات معيارية مجهزة (Parameterized Queries).
- عزل كامل للبيانات بين حسابات التجار المتعددة ومنع وصول أي مستخدم لبيانات حساب لا ينتمي إليه برمجياً.

### 4.3 الاعتمادية والتوافر (Availability & Reliability)
- نسبة الجاهزية التشغيلية المستهدفة (Uptime): لا تقل عن 99.9%.
- خطة نسخ احتياطي يومي آلي لقاعدة البيانات PostgreSQL مع حفظ النسخ مشفرة واختبار الاسترجاع شهرياً.
- معالجة انقطاع اتصال الموبايل عبر التخزين المؤقت المحلي (Local SQLite via Drift) وإعادة المحاولة التلقائية.
